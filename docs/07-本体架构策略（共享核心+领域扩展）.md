# 本体架构策略（共享核心 + 领域扩展）

> **文档版本**：v1.0
> **生成日期**：2026-08-08
> **文档类型**：权威规格（design doc）
> **状态**：待评审（仅审阅，未改动生产）
> **目标**：回答 JKBuddy 平台级本体组织问题——在「集中（单一中央本体）/ 分散（各 MCP、Skill 各自本体）/ 混合（共享核心 + 领域扩展）」三方案中给出推荐与落地规范。
> **核心结论**：采用**混合方案**——共享核心本体承载跨系统稳定语义（企业/部门/人员/审批/数据权限/通用枚举），领域本体承载绑定数据源的具体语义（投资 DWD、资产表），Skill 不持有语义、仅做"本体→MCP 操作适配"，二者靠 **import 单向依赖 + 版本化治理** 结合。

> **配套文档**：[01-JKBuddy产品设计蓝图.md](01-JKBuddy产品设计蓝图.md)（平台总览）、[04-本体层落地与组件边界设计.md](04-本体层落地与组件边界设计.md)（单系统本体边界）、[06-若依系统MCP化改造与数据权限设计.md](06-若依系统MCP化改造与数据权限设计.md)（多业务系统 MCP 化，资产系统样例）
> **前置阅读**：04 定义单系统内本体边界与单一事实源；06 确立"每业务系统独立 MCP Server"架构。本文档回答"当 JKBuddy 扩展为多业务系统平台时，本体如何在共享与分散间组织"。

---

## 1. 背景与决策问题

### 1.1 现状（方案B 雏形）

- 当前本体为**投资系统独占**：`mcp-inv-server-v2/ontology/ontology.yaml` 是投资系统语义的**单一事实源（SSOT）**，深绑定 9 个 DWD 视图（`dwd_fund` / `dwd_subfund` / `dwd_project` 等），包含对象类型（Fund/Subfund/Project/LP）、关系（INVESTS_IN）、规则、视图级字段白名单（`allowed_fields`）。
- 它通过生成器产出两类投影：**人读投影**（渲染进 SKILL 语义段）与**机读投影**（运行时白名单 / `get_ontology` 内省）。详细见 [04 文档](04-本体层落地与组件边界设计.md)。

### 1.2 决策问题的出现

JKBuddy 已从"单投资系统"演进为**多业务系统平台**（见 [01 蓝图](01-JKBuddy产品设计蓝图.md) 与 [06 文档](06-若依系统MCP化改造与数据权限设计.md)）：

| 业务系统 | MCP Server | 领域 | 本体现状 |
|---------|-----------|------|---------|
| 投资系统 | `mcp-inv-server-v2` | 投资查询 | 已有投资领域本体（绑定 DWD） |
| 资产系统 | （规划独立 MCP Server） | 查询 + 审批 + 协同 | 待建资产领域本体 |

**决策问题**：当存在多个业务系统时，本体应**集中成一个全 JKBuddy 共享本体**、**分散到各 MCP/Skill**、还是**二者结合**？

---

## 2. 三方案辩证分析

### 方案A：全集中（单一中央本体，覆盖所有产品）

- **优点**：全局唯一语义源，跨系统一致性最强；Agent 认知单一。
- **缺陷**：
  1. **深绑定数据源**——投资本体锚定 DWD 视图与字段白名单，资产本体锚定若依表与审批流，两者数据模型、安全约束、发布节奏都不同，强行合并成一份会**巨型、缠绕、单点故障**。
  2. **锁步发布**——集中使各系统无法独立发布，资产系统加字段会牵动投资系统。
  3. **语义漂移"升级"**——04 §2.2 的单系统漂移会放大为跨系统漂移，治理难度指数上升。
- **判词**：适合单一系统，不适合多系统平台。

### 方案B：全分散（各 MCP/Skill 各自本体，当前态）

- **优点**：领域自治，贴合现有 `ontology.yaml` 与 DWD 绑定；各系统独立发布。
- **缺陷**：**交叉概念重复定义**，以下概念几乎每个业务系统都有，各自复制必然漂移：
  - 组织：企业(company)、部门(dept)、人员(user)
  - 审批：approval 状态/节点/流程
  - 数据权限：`data_scope`、可见范围
  - 通用枚举：金额单位(万元)、业务线分类骨架、时间口径
- **判词**：解决了单系统一致性，却让平台级"企业/审批/权限"语义各自为政——A1/A2 面对多系统时无法统一认知。

### 方案C：混合（共享核心 + 领域扩展）——**推荐**

- **共享核心本体（Platform Ontology）**：承载**跨系统、与数据源无关**的稳定概念——企业/部门/人员/组织、审批(approval)、数据权限(data_scope)、通用枚举(金额单位/业务线骨架)、通用关系。即"抽象出来给所有产品"的部分。
- **领域本体（Domain Ontology per MCP）**：投资领域（Fund/Subfund/Project/INVESTS_IN + DWD 白名单）、资产领域（资产/处置/审批实例），各自 import 共享核心、延续现有 `ontology.yaml`。
- **Skill 层**：延续 04 Q3，**不拥有语义 SSOT**，只做"本体→MCP 操作适配"，引用对应领域本体。
- **关系**：领域本体 `imports` 共享核心（**单向依赖，禁止领域间互引**）。

## 3. 推荐方案：混合（共享核心 + 领域扩展）

### 3.1 分层定义

| 层 | 命名空间 | 内容 | 绑定数据源？ | 治理 |
|----|---------|------|------------|------|
| 共享核心 | `platform` | 企业/部门/人员/组织、审批、数据权限、通用枚举、通用关系 | 否 | 中央评审 + 严格版本化 |
| 领域本体 | `domain:investment` | Fund/Subfund/Project/LP + DWD 白名单 | 是 | 领域自治，锁定核心版本 |
| 领域本体 | `domain:asset` | 资产/处置/审批实例 | 是 | 领域自治，锁定核心版本 |
| Skill 适配 | —（引用领域本体） | 本体→MCP 操作适配 | — | 随领域本体 |

### 3.2 共享核心 vs 领域本体的边界判定准则

| 判定问题 | 进共享核心 | 进领域本体 |
|---|---|---|
| 被 ≥2 个业务系统复用？ | 是（企业/审批/权限/单位） | 否（仅本领域用） |
| 语义是否跨系统稳定？ | 稳定（"万元"、"data_scope"含义不变） | 绑定具体数据源/业务域（DWD 字段） |
| 是否绑定某 MCP 的具体表/视图？ | 否 | 是（`source_view: dwd_fund`） |
| 是否含数据源级安全白名单？ | 否 | 是（`allowed_fields` 视图专属） |

**关键判据：是否绑定数据源（view/table）。** 绑定 → 领域；不绑定 → 共享核心。这正好把 04 的"安全白名单"归领域、把"企业/审批/权限/单位"归共享。

## 4. 落地形态（具体建议）

### 4.1 命名空间与文件布局

```yaml
# 共享核心：JKBuddy/platform/ontology.yaml（平台级，版本化）
namespace: platform
object_types:
  Company:  { label: 企业/金控公司, ... }   # 跨系统
  Dept:     { label: 部门, ... }
  User:     { label: 人员, ... }
  Approval: { label: 审批实例, ... }         # 审批/权限/协同 通用骨架
enums:
  money_unit: [万元]                          # 统一金额单位
  data_scope: [ALL, CUSTOM, DEPT, DEPT_DESC, SELF]

# 领域本体：mcp-inv-server-v2/ontology/ontology.yaml（投资，延续现状）
namespace: domain:investment
imports: [platform]
object_types:  Fund / Subfund / Project / LP ...   # 绑定 DWD
link_types:    INVESTS_IN ...
security:      dwd_fund.allowed_fields ...          # 视图专属白名单

# 领域本体：mcp-asset-server/ontology/ontology.yaml（资产，06 目标）
namespace: domain:asset
imports: [platform]
object_types:  资产 / 处置单 ...
link_types:    处置审批 / 协同推送 ...
```

### 4.2 生成器与运行时加载

- 每个 MCP Server 启动时，合并 `platform + 自身领域`，渲染本服务器的白名单与 SKILL 语义段（复用 04 §4.3 运行时加载机制）。
- `get_ontology(scope)` 内省工具增加 scope 区分：`platform` / `domain:xxx` / 合并视图。

### 4.3 版本治理

- 共享核心**严格版本化**（semver）；领域本体**锁定所依赖的核心版本**。
- 共享核心变更走**中央评审**；领域本体各自独立评审、独立发布。

---

## 5. 反模式防控（延续 04 §7.2）

1. **禁止领域本体复制共享核心概念**——用 `import` 而非抄写，避免二次漂移。
2. **禁止共享核心膨胀**——只放"数据源无关 + 跨域稳定"概念，不放领域专属内容（用 §3.2 门禁 + 评审拦截）。
3. **禁止领域间互相 import**——依赖必须单向（领域 → 核心），防止依赖环。

---

## 6. 风险与权衡

| 风险 | 对策 |
|------|------|
| 共享核心被塞入领域专属内容 → 膨胀 | "是否绑定数据源"门禁 + 中央评审 |
| 共享核心变更影响面大 | 版本化 + 中央评审 + 领域锁定版本 |
| 生成器需处理多源合并复杂度 | 合并只发生在 import 层，复用 04 生成器 |
| 初期过度设计 | **渐进式**：先保留投资领域本体不动，抽离"企业/部门/金额单位"等确定跨域项入核心，跑通后再扩容 |

---

## 7. 渐进落地建议

1. **第一步**：投资领域本体保持 `mcp-inv-server-v2/ontology/ontology.yaml` 不动，仅新建 `platform` 共享核心（先放企业/部门/金额单位/data_scope 等确定跨域项）。
2. **第二步**：投资领域本体加 `imports: [platform]`，验证生成器多源合并。
3. **第三步**：资产系统 MCP Server（06 规划）建 `domain:asset`，import 同一共享核心。
4. **第四步**：审批/协同等跨域概念在共享核心沉淀稳定后，向各领域推广。

## 9. 验收标准（评审通过后）

1. 共享核心仅含跨系统稳定概念，不含任何 `source_view` 绑定。
2. 每个领域本体均通过 `imports: [platform]` 复用共享概念，无重复定义。
3. 领域本体之间无直接依赖（单向：领域 → 核心）。
4. 生成器可正确合并 `platform + 领域` 渲染白名单与 SKILL 语义段。
5. 新增业务系统只需新建领域本体 + import 共享核心，无需改动核心。

## 10. 附录：本体层示例 YAML

> 完整示例见 [ontology-hybrid-example.yaml](ontology-hybrid-example.yaml)。下方为同一示例的内嵌副本，展示共享核心与领域扩展的具体定义格式。

```yaml
# =============================================================================
# JKBuddy 本体层示例（混合架构：共享核心 + 领域扩展）
# 实际落地上，共享核心与各领域本体分文件存放，并通过 imports 单向依赖结合：
#   JKBuddy/platform/ontology.yaml             # 共享核心（namespace: platform）
#   mcp-inv-server-v2/ontology/ontology.yaml   # 领域：投资（imports: [platform]）
#   mcp-asset-server/ontology/ontology.yaml    # 领域：资产（imports: [platform]）
# 依赖方向（单向，禁止领域间互引）：platform ← domain:investment / domain:asset
# 关键判定：是否绑定数据源(view/table)？ 绑定→领域；不绑定→共享核心。
# =============================================================================


# =============================================================================
# 一、共享核心本体（JKBuddy/platform/ontology.yaml）
#    仅承载跨系统、与数据源无关的稳定语义。禁止出现 source_view / allowed_fields。
# =============================================================================
namespace: platform
version: "1.0"

object_types:
  Company:
    label: 企业/金控公司
    properties:
      - {name: company_id,    type: string,  desc: "企业系统唯一编号"}
      - {name: company_name,  type: string,  desc: "企业/公司名称"}
      - {name: company_type,  type: string,  desc: "企业类型（母基金/资本运作/风投等）"}
      - {name: parent_id,     type: string,  desc: "上级公司编号（支持层级）"}

  Dept:
    label: 部门
    properties:
      - {name: dept_id,       type: string,  desc: "部门编号"}
      - {name: dept_name,     type: string,  desc: "部门名称"}
      - {name: ancestors,     type: string,  desc: "祖先链（支持'本部门及以下'数据范围）"}

  User:
    label: 人员
    properties:
      - {name: user_id,       type: string,  desc: "用户编号"}
      - {name: user_name,     type: string,  desc: "登录名（对应蓝凌 SSO loginName）"}
      - {name: dept_id,       type: string,  desc: "所属部门"}
      - {name: role_ids,      type: array,   desc: "角色编号列表"}

  Approval:
    label: 审批实例
    properties:
      - {name: approval_id,   type: string,  desc: "审批实例编号"}
      - {name: biz_type,      type: string,  desc: "审批所属业务类型"}
      - {name: status,        type: string,  desc: "审批状态"}
      - {name: current_node,  type: string,  desc: "当前审批节点"}
      - {name: applicant,     type: string,  desc: "申请人"}
      - {name: apply_time,    type: datetime, desc: "发起时间"}

link_types:
  BELONGS_TO:
    label: 从属关系（用户/部门 → 组织）
    source_object: [User, Dept]
    target_object: [Company, Dept]
    properties:
      - {name: rel_role,      type: string,  desc: "从属角色"}

  APPROVES:
    label: 审批关系（用户审批实例）
    source_object: [User]
    target_object: [Approval]
    properties:
      - {name: opinion,       type: string,  desc: "审批意见"}
      - {name: approve_time,  type: datetime, desc: "审批时间"}

enums:
  money_unit:
    - 万元
  data_scope:
    - ALL
    - CUSTOM
    - DEPT
    - DEPT_DESC
    - SELF
  common_status:
    - PENDING
    - APPROVED
    - REJECTED
    - WITHDRAWN

rules:
  - id: R-DATA-SCOPE-JUDGEMENT
    scope: GLOBAL
    desc: "数据权限判定"
    definition: "数据权限(data_scope)由若依服务端依据当前登录用户自行判定，agent/MCP 不做分类识别，仅透传已认证身份"

  - id: R-MONEY-UNIT
    scope: GLOBAL
    desc: "金额单位"
    definition: "所有金额字段单位统一为万元"

  - id: R-IDENTITY-SERVER-SIDE
    scope: GLOBAL
    desc: "身份服务端解析"
    definition: "身份(loginName→sys_user)由 MCP 服务端解析，禁止客户端自报 user_id/data_scope"


# =============================================================================
# 二、领域扩展：投资系统（mcp-inv-server-v2/ontology/ontology.yaml）
#    绑定 DWD 视图，import 共享核心。以下为本示例的"投资"节选（非全量）。
# =============================================================================
namespace: domain:investment
version: "1.0"
imports: [platform]

object_types:
  Fund:
    source_view: dwd_fund
    primary_key: fund_id
    label: 基金基本情况
    properties:
      - {name: fund_id,        type: string,  desc: "基金在系统中唯一编号"}
      - {name: fund_name,      type: string,  desc: "基金名称"}
      - {name: fund_type,      type: string,  desc: "基金类型"}
      - {name: fund_phase,     type: string,  desc: "基金阶段"}
      - {name: company_name,   type: string,  desc: "基金所属的金控公司"}
      - {name: cap_date,       type: datetime, desc: "基金成立备案日期"}
      - {name: total_size,     type: decimal, unit: 万元, desc: "基金规模"}
      - {name: invest_amount,  type: decimal, unit: 万元, desc: "投资金额"}
      - {name: exit_amount,    type: decimal, unit: 万元, desc: "退出金额"}

  Project:
    source_view: dwd_project
    primary_key: proj_id
    label: 项目基本情况
    properties:
      - {name: proj_id,        type: string,  desc: "项目在系统唯一编号"}
      - {name: proj_name,      type: string,  desc: "项目名称"}
      - {name: phase,          type: string,  desc: "项目阶段"}
      - {name: biz_line,       type: string,  desc: "业务线（中文值，如 股权项目/融资租赁）"}
      - {name: company_name,   type: string,  desc: "项目所属金控公司"}
      - {name: invest_amount,  type: decimal, unit: 万元, desc: "投资金额"}
      - {name: exit_amount,    type: decimal, unit: 万元, desc: "退出金额"}

link_types:
  INVESTS_IN:
    source_view: dwd_all_biz
    source_object: [Fund, Subfund, LP]
    target_object: [Project, SubfundProject, Subfund, Fund]
    subtypes: [FUND2PROJ, SUBFUND2PROJ, FUND2SUBFUND, LP2FUND]
    label: 全部投资关系
    properties:
      - {name: biz_type,      type: string,  desc: "业务类型（biz_type），4 种互斥"}
      - {name: investor_name, type: string,  desc: "投资人名称"}
      - {name: investee_name, type: string,  desc: "被投资人名称"}
      - {name: company_name,  type: string,  desc: "负责该投资的金控公司"}
      - {name: flow_amt,      type: decimal, unit: 万元, desc: "实际出资额"}
      - {name: flow_time,     type: datetime, desc: "出资流水时间"}

rules:
  - id: R-COMPANY-ATTRIBUTION
    scope: INVESTS_IN
    desc: "投资归属规则"
    definition: "投资方实体所属的金控公司；LP2FUND 回退为被投资方（基金），LP 为外部方无金控公司"

  - id: R-COMMITTED-AMT-SCOPE
    scope: INVESTS_IN
    desc: "committed_amt 有效范围"
    definition: "committed_amt 仅在 biz_line 为 FUND 和 LP 时有业务意义；项目类不得以 committed_amt 作投资额口径，应使用 flow_amt"

security:
  dwd_fund:
    allowed_fields: [fund_id, fund_name, fund_type, fund_phase, company_name, cap_date, invest_amount, exit_amount, total_size]
```
