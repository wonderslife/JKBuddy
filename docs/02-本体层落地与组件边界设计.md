## 1. 术语澄清

> 为避免歧义，先统一本项目语境下的术语。

| 术语 | 本项目含义 |
|------|-----------|
| **MCP** | **Model Context Protocol**（模型上下文协议），Anthropic 提出的开放标准。本项目指基于该协议实现的 `mcp-inv-server-v2` 服务端，承担数据访问与查询执行。本文讨论组件边界时，**MCP 特指"查询执行 + 结构安全校验层"**，是协议化执行层而非业务编排平台。 |
| **SKILL** | `investment-dwd-query` 技能，位于 `LibreChat/skill/investment-dwd-query/SKILL.md`，当前为"技术实现层"。 |
| **Agent 指令** | LibreChat 中 A1（纯意图分类器）与 A2（执行器）的 Instructions（System Prompt）。 |
| **本体（Ontology）** | 拟引入的、作为"语义单一事实源（SSOT）"的对象类型 / 关系类型 / 属性 / 业务规则定义。 |
| **DWD 视图** | `mcp-inv-server-v2/sql/dwd_views.sql` 定义的 9 个语义视图（含 `dwd_all_biz`）。 |
| **投影（Projection）** | 本体定义的下游派生产物。人读投影 = 渲染进 SKILL 的语义文本；机读投影 = 生成进 `base.py` 的白名单代码。 |

## 2. 现状四层架构与问题（引入本体前）

### 2.1 当前各组件定位

| 组件 | 当前定位 | 实际承载的知识 | 问题 |
|------|---------|--------------|------|
| **MCP 服务端** | 查询执行 + 白名单校验 | docstring 与 `base.py` 注释中**携带大量语义**（如 `company_name` 语义、`biz_line` 映射）；`query_all_biz` docstring 甚至写了"仅用于宏观统计，禁止查询特定项目"这一**业务约束** | 语义被硬编码在代码里，与文档 / SKILL 三方维护 |
| **SKILL** | 技术实现层"怎么查" | 字段/关系语义 + 工具路由/参数映射（v1.15 已做过指令/Skill 去重，但语义与操作仍耦合在同一 SKILL.md 文件中） | 语义与操作耦合于同一文件，是漂移重灾区（v1.17 前出现过"dwd_all_biz 无 company_name"过期说法） |
| **Agent 指令(A1/A2)** | 行为层"怎么答" | 数据忠实性、防拼接、分页、循环终止等行为规则 | 行为规则与语义规则边界清晰，v1.15 已归位，**相对干净** |
| **本体(Ontology)** | （待引入） | 应承载：对象类型、关系类型、属性、业务规则 = 语义单一事实源 | 尚不存在 |

### 2.2 核心矛盾

**语义知识**（字段含义、关系、业务规则）目前**分散且无权威源**地存在于 MCP 代码、SKILL、文档三处；而**行为知识**（怎么答）已经有了清晰归属（指令层）。

引入本体的本质，是**为"语义"补上缺失的单一事实源（SSOT）**，让"语义"与"行为"两条线都各归其位：

```
语义：本体(SSOT)  → 生成/渲染 → MCP 白名单 + SKILL 语义段
行为：Agent 指令(SSOT)  → 约束 → 输出规范
```

## 3. 引入本体后必须解决的关键问题

采用苏格拉底式框架，把决策点拆成 6 个"必须回答的问题"。

> **依赖链**：6 个问题存在依赖关系——Q1（权威级别）→ Q2（双投影方案）→ Q3/Q4/Q5（各组件边界）→ Q6（治理闭环）。建议按序阅读。

### Q1：本体的"权威性"落在哪一层？构建期还是运行期？

- **问题**：本体是**编译期产物**（生成静态 SKILL + 白名单，提交进仓库）还是**运行期服务**（模型 / Skill 运行时实时拉取）？
- **辩证**：
  - 编译期：简单、零运行时依赖、可进 CI 校验；但变更需重新部署。
  - 运行期：动态、永不漂移；但引入新依赖与网络延迟。
- **建议**：**分两步**——先编译期（`ontology.yaml` + 生成器），验证价值后再演进为运行期元数据服务。文档中需**显式声明本体的权威级别**，避免团队误用。

### Q2：本体有两个"消费者"（LLM 与机器），如何防止两条投影分叉？

- **问题**：LLM 需要**人类可读**的本体投影（进入 SKILL/指令）；MCP 需要**机器可读**投影（白名单、字段校验）。若同一本体被手工复制成两份，必然漂移。
- **建议**：**单一 `ontology.yaml` + 双投影生成**。人读投影渲染进 SKILL，机读投影生成 `base.py` 白名单。**禁止手工维护任何投影**，只允许改本体。

### Q3：SKILL 到底该保留什么、剥离什么？

- **问题**：SKILL 现在混合语义 + 操作。引入本体后，SKILL 的语义部分（字段含义、关系、company_name 归因）应**上移归本体**；操作部分（工具路由、参数映射、两级策略）是"本体语义 → MCP 执行"的**适配器**，应保留。
- **建议**：SKILL 重定位为 **"本体→MCP 的操作适配层"**，只保留"怎么把本体定义的查询意图翻译成 MCP 调用"，语义定义一律引用本体、不再重复书写。

### Q4：MCP 服务端是否要保持"哑执行器"？语义该不该进 MCP？

- **问题**：MCP 若在 docstring 或代码中写入"查询关系应优先走 `dwd_all_biz`"这类路由策略，就会向上漂移成业务层；若完全不知道语义，又无法做字段级安全校验。
- **辩证**：实际上当前 `query_all_biz` 的 docstring 已携带"仅用于宏观统计，禁止查询特定项目"这一**业务约束**，这正是 MCP 承载业务语义的现存隐患。引入本体后，此类业务约束应上移至本体规则，MCP 只保留"合法字段 / 合法聚合 / 合法关系"的**结构约束**——这恰好可由本体生成的白名单提供。所以 MCP 保持"**结构安全、语义无知**"：它知道"哪些字段合法、哪些可分组、哪些可前缀"，但**不**知道"查关系应该先走 `dwd_all_biz`"。
- **建议**：MCP = 哑执行器 + 本体生成的结构白名单。当前 docstring 中的业务约束（如"仅用于宏观统计"）应迁移至本体规则段。

### Q5：Agent 指令（行为层）与本体如何解耦？

- **问题**：数据忠实性、防拼接、分页、循环终止等**行为规则**，与**语义定义**（字段含义）是两类东西。行为规则不是本体能承载的（本体的 Actions 只描述"可执行操作"，不描述"输出时不得过滤"）。
- **建议**：**行为规则 100% 留在指令中，本体不承载行为规则**。指令只引用本体 / 本体派生 SKILL 的技术定义，不重复语义。这是 v1.15 去重归位的延续，本体让它**可机器校验**。

### Q6：变更如何传播不失控？（治理闭环）

- **问题**：加一个字段（如本次 `company_name`），牵动 MCP 白名单、SKILL、指令、文档四处。如何保证只改一处、其余自动同步？
- **建议**：**变更必须先改本体 → 生成器重出白名单 + SKILL → 漂移检查器比对 → 才允许进代码**。参照现有 `verify_tool_fields.py`（位于 `mcp-inv-server-v2/verify_tool_fields.py`）的审计思路，把"字段漂移检查"升级为"本体-白名单-SKILL 一致性检查"。

## 4. 调整后的组件功能边界（目标态）

> ⚠️ 下表为**引入本体后的目标态**。当前代码中 `INVESTS_IN` 等关系类型尚未实现，`ontology.yaml` 尚未创建。本表用于指导落地实施的方向，不代表当前代码现状。

| 组件 | 职责边界 | 必须承载 | 禁止承载 |
|------|---------|---------|---------|
| **本体** | 语义单一事实源 | 对象类型、关系类型（如 `INVESTS_IN`）、属性、业务规则（如 `R-COMPANY-ATTRIBUTION`） | 行为规则、输出格式、工具调用顺序 |
| **MCP 服务端** | 协议化执行 + 结构安全校验 | 白名单校验（由本体生成）、DWD 视图查询、返回原始行 | 业务路由（哪张表先查）、语义解释、去重/过滤 |
| **SKILL** | 本体→MCP 操作适配器 | 工具路由（两级策略）、参数值映射、biz_type/biz_line 转换 | 字段/关系语义定义（引用本体）、输出行为 |
| **A1 指令** | 纯意图分类器 | 意图分类、参数抽取、澄清终止 | 调工具、输出结果、语义定义 |
| **A2 指令** | 行为层"怎么答" | 数据忠实性、防拼接、分页、追问必重查、循环终止 | 语义定义、技术路由（引用 SKILL） |

### 4.1 依赖方向（单向无环 + 反馈流）

```
本体 --生成/校验--> MCP 白名单
本体 --渲染--> SKILL(语义段)
SKILL --调度--> MCP(调用工具) --返回原始行--> SKILL --呈现--> A2 --> 用户
A2 指令 --引用--> SKILL(技术实现)
A1 --Handoff--> A2(只传分类与参数)
MCP --查询--> DWD 视图 --读--> 数据库
CI --漂移检查--> [本体 vs 白名单 vs SKILL] --不一致则阻断--> 发布
```

### 4.2 本体定义文件 Schema（`ontology.yaml`）

> 以下是本体定义文件的结构化 Schema 与示例。开发团队据此创建 `mcp-inv-server-v2/ontology/ontology.yaml`，作为所有语义定义的单一事实源。

```yaml
# ontology.yaml - 本体定义文件（单一事实源）
# 路径：mcp-inv-server-v2/ontology/ontology.yaml
# 权威级别：运行期（Phase 2）。MCP 启动/首次导入时自动加载本文件，
#           生成机读投影（base.py 运行时白名单）与人读投影（SKILL 语义段）。
version: "1.0"

# ── 对象类型定义 ──
object_types:
  Fund:
    source_view: dwd_fund
    primary_key: fund_id
    properties:
      - {name: fund_name, type: string, desc: "基金名称"}
      - {name: company_name, type: string, desc: "基金所属金控公司"}
      - {name: fund_type, type: string, desc: "基金类型"}
      - {name: total_size, type: decimal, unit: 万元, desc: "基金规模"}
      - {name: invest_amount, type: decimal, unit: 万元, desc: "投资金额"}
      - {name: exit_amount, type: decimal, unit: 万元, desc: "退出金额"}

  Subfund:
    source_view: dwd_subfund
    primary_key: subfund_id
    properties:
      - {name: subfund_name, type: string, desc: "子基金名称"}
      - {name: company_name, type: string, desc: "子基金所属金控公司"}

  Project:
    source_view: dwd_project
    primary_key: proj_id
    properties:
      - {name: proj_name, type: string, desc: "项目名称"}
      - {name: company_name, type: string, desc: "项目所属金控公司"}
      - {name: biz_line, type: string, desc: "业务线"}

  LP:
    source_view: dwd_lp2fund
    primary_key: lp_id
    properties:
      - {name: lp_name, type: string, desc: "出资人名称"}
      - {name: lp_type, type: string, desc: "出资人类型"}

# ── 关系类型定义 ──
link_types:
  INVESTS_IN:
    source_view: dwd_all_biz
    source_object: [Fund, Subfund, LP]        # 投资方
    target_object: [Project, Subfund, Fund]   # 被投资方
    subtypes: [FUND2PROJ, SUBFUND2PROJ, FUND2SUBFUND, LP2FUND]
    properties:
      - {name: company_name, type: string, desc: "投资归因金控公司"}
      - {name: committed_amt, type: decimal, unit: 万元, desc: "承诺出资额"}
      - {name: flow_amt, type: decimal, unit: 万元, desc: "实际出资额"}
      - {name: flow_time, type: datetime, desc: "出资流水时间"}
      - {name: biz_line, type: string, desc: "业务线"}

# ── 业务规则定义 ──
rules:
  - id: R-COMPANY-ATTRIBUTION
    scope: INVESTS_IN
    desc: "company_name 归因规则"
    definition: "投资方实体所属公司；LP2FUND 回退为被投资方基金公司"

  - id: R-NO-CROSS-BIZLINE-SUM
    scope: INVESTS_IN
    desc: "禁止跨业务线加总金额"
    enforce_in: [stat_investment_summary]

  - id: R-ALL-BIZ-MACRO-ONLY
    scope: query_all_biz
    desc: "dwd_all_biz 仅用于宏观统计"
    definition: "禁止用于查询特定项目或基金列表，应使用专表工具"

# ── 安全约束（生成白名单的依据）──
security:
  dwd_all_biz:
    allowed_fields: [biz_type, investor_id, investor_name, investee_id, investee_name, biz_line, company_name, flow_time, committed_amt, flow_amt]
    group_by_fields: [biz_type, biz_line, investor_name, investee_name, company_name]
    prefix_match_fields: [investor_name, investee_name, company_name]
    null_check_fields: [committed_amt, flow_amt]
    amount_range_fields: [committed_amt, flow_amt]
    date_range_fields: [flow_time]
    stable_order_field: biz_type
    default_fields: [biz_type, investor_id, investor_name, investee_id, investee_name, biz_line, company_name, committed_amt, flow_amt, flow_time]

  dwd_fund:
    allowed_fields: [fund_id, fund_name, fund_type, fund_phase, dept_id, company_name, cap_date, invest_amount, exit_amount, subscribed_amt, total_size]
    group_by_fields: [fund_type, fund_phase, company_name, dept_id]
    prefix_match_fields: [fund_name, company_name]
    # ... 其余视图按 base.py 现有白名单补全
```

### 4.3 运行时自动加载机制（Phase 2 已落地）

> **核心结论**：本体不再通过"命令生成静态白名单"生效，而是 **MCP 启动/首次导入时自动加载**，改 `ontology.yaml` → 重启即生效，**全程无需任何同步命令**（`write-base` 已废弃）。端到端已实测验证（改副本加字段 → 全新进程启动 → 运行时白名单即时识别新字段）。

**加载链路**：

```
MCP 进程启动
  → 首次导入 tools/base.py
  → get_whitelists()        @lru_cache 懒加载单例（进程内只算一次，fail-fast）
  → get_ontology()          @lru_cache 进程级缓存（本体只解析一次）
  → load_ontology()         pydantic 校验 ontology.yaml
  → generate_whitelists()   产出机读投影（白名单容器）
  → 注入 10 个运行时常量（ALLOWED_FIELDS / GROUP_BY_FIELDS / DEFAULT_FIELDS ...）
```

**关键设计**：

| 设计点 | 说明 |
|--------|------|
| 懒加载单例 | `get_whitelists()` 用 `@lru_cache(maxsize=1)`，模块加载时立即调用一次，启动即注入 |
| fail-fast | 本体加载/校验失败直接抛错，**绝不**静默降级为空白名单（否则等于无白名单，有 SQL 注入风险） |
| 路径可覆盖 | `INV_MCP_ONTOLOGY_PATH` 可指定本体路径，默认 `<项目根>/ontology/ontology.yaml` |
| 单次解析 | `get_ontology()` 进程级缓存，运行时白名单与本体内省工具共用同一份本体，避免重复解析 |
| 内省工具 | 新增第 12 个 MCP 工具 `get_ontology(scope)`，Agent 可运行时拉取对象/关系/规则/视图白名单 |

## 5. 一致性保证

### 5.1 三把锁

1. **生成器锁**：`ontology.yaml` → 白名单 + SKILL 语义段，杜绝手工双写。
2. **漂移检查锁**：CI / 脚本比对"本体 vs 已提交白名单 vs 已提交 SKILL"，任一不一致即告警（复用 `verify_tool_fields.py` 模式）。
3. **行为/语义分离锁**：行为规则只进指令，语义只进本体，从结构上防串层。

### 5.2 可扩展性对照

| 场景 | 现在的改法 | 引入本体后的改法 | 新改法的风险 |
|------|-----------|----------------|------------|
| 新增字段（如本次 `company_name`） | 改 DDL + 改 base.py 白名单 + 改 SKILL + 改指令 + 改文档，易漏 | **只改本体** → 生成器重出白名单 + SKILL → 校验通过即可 | 生成器 bug 可能导致全量白名单错误，需配套漂移检查 |
| 新增业务域/关系 | 手写新工具 + 改 SKILL 路由 + 改指令 | 本体加对象 + 关系 → 生成器补白名单 → SKILL 适配器加一行路由 | 本体 schema 约束不足可能导致非法定义 |
| 调整业务规则（如金额口径） | 改 SKILL + 改 MCP + 改文档 | 改本体规则 → 生成器/校验器同步 | 规则变更影响面大，需回归测试 |

### 5.3 职责矩阵（RACI）

> R = Responsible（执行） / A = Accountable（负责） / C = Consulted（咨询） / I = Informed（知会）

| 任务 | 本体维护者 | 后端开发 | AI/Agent 开发 | QA |
|------|-----------|---------|--------------|-----|
| 修改 `ontology.yaml` | R/A | C | C | I |
| 运行生成器 | I | R | A | I |
| 漂移检查 | I | R | C | A |
| 更新 SKILL.md（语义段） | I | C | R/A | C |

## 6. 落地迁移步骤

1. **语义抽取**：从 SKILL 语义段、`base.py` docstring、`summary.py` 注释中抽取出对象 / 关系 / 属性 / 规则，写入 `ontology.yaml`。
2. **写生成器**：`ontology.yaml` → 生成 `base.py` 白名单（机读投影）+ 渲染 SKILL 语义段（人读投影）。
3. **写漂移检查器**：比对生成结果与仓库已提交内容，纳入 CI。
4. **重定位 SKILL**：删除其语义定义，只保留工具路由 / 参数映射 / 两级策略，语义改引用本体。
5. **（可选）MCP 元数据能力**：新增一个 `get_ontology` 类内省工具，让 A2 运行时拉取最新定义，彻底消灭指令 / SKILL 过期。
6. **治理门禁**：把"本体变更 + 生成 + 校验"作为发布前置条件，任何字段 / 规则变更先过本体。

### 6.1 端到端示例：以 `company_name` 字段新增为例

> 以 v1.17 已完成的 `company_name` 字段新增为案例，展示"本体驱动"的完整流程。

**Step 1：修改本体定义**（`ontology.yaml`）

  - id: R-COMPANY-ATTRIBUTION

**Step 2：重启 MCP（本体运行时自动加载白名单）**

## 7. 辩证提醒

### 7.1 退路：暂不引入本体时的最小改进

> 若团队评估后认为本体层暂不落地，建议至少做以下最小改进，以缓解当前语义分散问题。

1. 将 `base.py` docstring 中的业务语义（如"仅用于宏观统计"）迁移至 SKILL，MCP docstring 只保留技术说明。
2. 扩展 `verify_tool_fields.py`，增加"SKILL 字段说明 vs base.py 白名单"一致性检查。
3. 任何字段变更必须同时改 `base.py` + `SKILL.md`，并由 verify 脚本强制校验。
4. 在 `SKILL.md` 顶部维护"字段变更检查清单"，确保新增字段时逐项更新。

> ⚠️ 退路方案无法解决"语义散落三方"的根本问题，仅是缓解措施。建议在退路运行 1-2 个迭代后评估是否升级为完整本体方案。

### 7.2 三个反模式与检测方法

- **⚠️ 反模式一：本体变成"第四个维护点"**
  - **表现**：生成器不落地，仍手工改白名单 / SKILL，本体反而增加负担。
  - **本质**：本体只有配合生成器才是 SSOT，否则只是又一张纸。
  - **检测方法**：`git diff` 检查 `base.py` / `SKILL.md` 是否有非生成器产出的手工编辑；CI 中运行 `git blame` 校验变更来源。

- **⚠️ 反模式二：把行为规则塞进本体**
  - **表现**：本体 rules 段出现"禁止过滤/不得去重/必须原样输出"等行为约束。
  - **本质**：本体的 Actions 只描述"可执行操作"，不描述"输出时不得过滤"。数据忠实性是 A2 行为，进本体就是串层。
  - **检测方法**：检查 `ontology.yaml` 的 rules 段是否包含"禁止/不得/必须输出"等行为关键词；若发现则告警"行为规则应迁移至 A2 指令"。

- **⚠️ 反模式三：MCP 开始知道业务路由**
  - **表现**：MCP docstring 或代码中出现"优先/第一级/默认视图/先查 dwd_all_biz"等路由策略。
  - **本质**：若 MCP 承载路由策略，它会退化成业务层，破坏"MCP=执行、SKILL=适配、本体=语义、指令=行为"的单向分层。
  - **检测方法**：CI 扫描 MCP 工具 docstring，匹配"优先|第一级|默认视图|先查|路由"等关键词；若发现则告警"业务路由应迁移至 SKILL"。
