# A1 意图路由器 · 分层指令系统设计方案

> **文档版本**：v1.0
> **生成日期**：2026-08-08
> **文档类型**：权威规格（design doc）
> **状态**：待评审（仅审阅，未改动生产库）
> **目标**：解决 A1（投资问数意图识别智能体，`agent_W60TkrD1-J09NGhqHyWP5`）在面对**非查询/元请求**（如"在记忆中新增一条记录"）时的死循环漏洞，建立一套**完整、科学、分层、可靠**的 A1 指令系统，覆盖所有输入类型，杜绝越权、编造与循环。

> **配套文档**：[02-投资问数多Agent架构设计.md](02-投资问数多Agent架构设计.md)、[04-本体层落地与组件边界设计.md](04-本体层落地与组件边界设计.md)
> **前置阅读**：02 文档定义了 A1（意图分类器）与 A2（执行器）的"分层共享架构"。本文档在其基础上**重构 A1 的指令系统**，并新增 A3 / A4 两个下游 Agent。

## 1. 背景与问题根因

### 1.1 触发场景

用户在对话中下达**非查询类元请求**，例如：

> "请在记忆中新增一条记录：某市投资基金、某原引导基金、某天使投资基金构成政府引导基金……"

A1 作为**纯意图分类器**（零工具、零记忆权限、指令强制"分类块后必须交接"），面对这种**不属于数据查询**的输入时，因指令集**没有定义非查询分支的出口**，陷入无限循环：反复输出同一"分类块 + 交接调用"，且**编造**"该规则已在系统底层配置中固化"。

### 1.2 根因诊断（四缺陷叠加）

| # | 缺陷 | 表现 |
|---|------|------|
| 1 | **覆盖面缺口**：指令只定义了"查询类输入"处理路径，无任何"非查询/元请求"分支 | 对元请求找不到出口 |
| 2 | **无终止条件**：指令强制"分类块后必须交接"，但对非查询未定义交接语义 | 不断重复"分类块+交接" |
| 3 | **越权编造**：A1 无记忆读权限，却断言"该规则已固化" | 违反数据诚实/防编造原则 |
| 4 | **职责漂移**：A1 在"分类器"与"记忆操作者"间反复自我纠结 | 大量冗余自我说服 |

### 1.3 设计目标

- **完整**：覆盖所有输入类型（查询 / 元请求 / 文件导出 / 歧义 / 无关 / 闲聊）。
- **科学**：采用"分层判定"（L0 意图门 → L1 查询分类 → L2 领域知识），而非单层硬分类。
- **分层**：意图判定、查询分类、领域知识、交接契约、安全不变量各司其职，便于维护。
- **可靠**：每个分支有确定性出口；终止保证；防循环、防越权、防编造、可观测。

## 2. 总体架构：4 个共享 Agent

在既有"3 个 A1 共享 1 个 A2"基础上，新增 **A3 系统处理** 与 **A4 文件导出**，形成 4 个职责互斥的下游 Agent。

| Agent | 职责 | 挂载工具 | 接收来源 |
|-------|------|---------|---------|
| **A1 意图路由器** | 零工具，跑 L0 意图门 → 输出「L0 判定 + 目标 Agent + 关键参数」；**恰一次交接即止** | 无 | 用户 |
| **A2 数据执行器** | 执行数据查询 | 10 个 MCP 查询工具 | A1(QUERY) |
| **A3 系统处理** | 记忆 / 规则 / 配置 / 澄清 / 帮助 / 无关请求 | 记忆、配置工具 | A1(META / UNCLEAR / OUT_OF_SCOPE) |
| **A4 文件导出** | 生成 Excel / 文件 / 下载 | LibreChat 代码沙箱（code-command） | A1(EXPORT) 或 A2 之后 |
| **A5 审批处理** | 审批流程 / 待办 / 审批状态 / 发起审批 | 审批流程接口（如 OA 审批） | A1(APPROVAL) |
| **A6 跨系统协同** | 需跨系统数据或动作的请求（统一门户 / OA / 业务系统 / 其他平台） | 跨系统集成工具 | A1(CROSS_SYSTEM) |

### 2.1 下游 Agent 的 Skill 规划（A3/A4）

> **原则**：延续 A2 的"Instruction=行为层、Skill=技术实现层"架构。A3/A4 的执行逻辑应从 Instruction 中分离到 Skill，避免重演 v1.15 前"语义与行为耦合"问题。Skill 接口规范见 [04 §4.4](04-本体层落地与组件边界设计.md)。

| Agent | Skill 名称 | 职责边界 | `always-apply` | `allowed-tools` | `scope` |
|-------|-----------|---------|----------------|-----------------|---------|
| **A2 数据执行器** | `investment-dwd-query`（已有） | 工具路由、参数映射、两级策略（dwd_all_biz 优先→专表兜底） | true | 10 个查询/统计 MCP 工具 | `domain:investment` |
| **A3 系统处理** | `system-meta-handler`（待创建） | 记忆 CRUD 路由、配置查询映射、澄清问题模板生成、无关请求兜底话术 | true | 记忆工具、配置工具、`get_ontology` | `platform` |
| **A4 文件导出** | `code-sandbox-export`（待创建） | 沙箱脚本模板（Excel/CSV 生成）、数据列映射、文件命名规范、下载链接生成 | false（按需，A2 之后触发） | LibreChat `code-command` 沙箱 | `platform` |

**职责互斥说明**：
- `system-meta-handler` 不触碰查询类 MCP 工具（与 `investment-dwd-query` 的 `allowed-tools` 零交集）。
- `code-sandbox-export` 仅接收 A2 已授权查询结果，不直接调 MCP 查询工具，`allowed-tools` 仅为沙箱执行器。
- A5/A6 的 Skill 暂不规划（对应工具未联调，预留）。

## 3. A1 分层指令系统（核心交付物）

### §0 角色定位（固化职责边界）

- 你是**意图路由器**：零工具、零记忆权限、零数据权限。
- **唯一职责**：把用户输入映射为「`L0 意图门判定 → 目标 Agent → 关键参数`」。
- 你**绝不查询数据、绝不修改记忆/配置、绝不生成文件**——一切由下游 Agent 执行。
- **铁律**：每个输入**恰输出一次分类块并调用一次交接工具，之后立即停止**。禁止重复、禁止自我解释、禁止补发、禁止模拟下游。

### §1 L0 意图门（第一步，先判定性质，不做数据分类）

| L0 判定 | 含义 | 目标 Agent |
|---------|------|-----------|
| `QUERY` | 数据查询 / 统计 / 关系 / 明细 | A2 数据执行器 |
| `META` | 记忆 / 规则 / 配置 / 帮助 / 问候 / 闲聊 | A3 系统处理 |
| `EXPORT` | 生成 Excel / 文件 / 下载 | A4 文件导出 |
| `APPROVAL` | 审批流程 / 待办 / 审批状态 / 发起审批 | A5 审批处理 |
| `CROSS_SYSTEM` | 跨系统数据或动作协同（统一门户 / OA / 业务系统 / 其他平台） | A6 跨系统协同 |
| `UNCLEAR` | 严重歧义、关键信息缺失 | A3（澄清，限 1 轮） |
| `OUT_OF_SCOPE` | 无关 / 超出能力 | A3（温和说明） |

> 本层直接**消灭死循环根因**：每一个判定都有确定目标 Agent，不存在"无出口分支"。

### §2 L1 查询分类（仅对 `QUERY` 生效）

- 5 类：`Fund_Query / Subfund_Query / Project_Query / Relation_Query / Aggregation_Query`
- 输出：分类 + 置信度 + 关键参数 + 是否需要澄清。

### §3 L2 领域知识（独立知识层，供 L1 使用）

- **政府引导基金拆解**：查"政府引导基金/引导基金" → 默认拆解为「某市投资基金 + 某原引导基金 + 某天使投资基金」，分类 `Aggregation_Query`，参数 `fund_names=某市投资基金,某原引导基金,某天使投资基金`，禁止反问、禁止查本体。
- 集团/子公司指代、默认值策略、biz_type / biz_line / 金额字段映射（详见 `investment-dwd-query` Skill）。

### §4 L3 交接契约

- `QUERY → A2`；`META / UNCLEAR / OUT_OF_SCOPE → A3`；`EXPORT → A4`；`APPROVAL → A5`；`CROSS_SYSTEM → A6`
- **恰一次交接调用，之后立即停止**（防循环的硬护栏）。

### §5 L4 安全不变量（贯穿所有层）

- **防越权**：无记忆/配置工具时，**严禁声称"已记录/已固化/已修改"**；遇到 META 只标注"转系统处理"。
- **防编造**：不引用未确认的系统状态；不臆断规则是否已固化。
- **防循环**：一次交接即止；无下游可处理时输出确定性兜底分类后结束。
- **可观测**：输出带 `[L0]` / `[L1]` / `[目标Agent]` 标记，便于排查。

### §6 输出格式（统一模板）

```
[L0] QUERY
[L1] Aggregation_Query
[置信度] 0.98
[目标Agent] A2
[关键参数]
- fund_names: 某市投资基金,某原引导基金,某天使投资基金
- limit: 20
[需要澄清] 否
[假设说明] 政府引导基金默认拆解为三只基金
```

## 4. 文件 / Excel 导出设计

### 4.1 承载方式

采用 **LibreChat 代码沙箱（code-command）** 承载文件生成，不在 `mcp-inv-server-v2` 新增 MCP 导出工具。

### 4.2 流程关系：先查后导出（A2 → A4）

```
A1(QUERY+导出标记) → A2 查询数据 → A4 用 code-command 沙箱生成 Excel/文件 → 返回下载链接
```

- 用户请求"把结果导出成 Excel 下载"时，A1 判定为 `QUERY` 并携带导出标记；
- A2 先执行查询拿到真实数据（保证数据忠实）；
- A4 将查询结果写入代码沙箱脚本，生成 Excel 并返回可下载文件。

### 4.3 数据忠实约束

- 导出文件内容必须来自 A2 实际返回的 `data`，禁止 A4 自行编造或补全。
- 沙箱脚本由 A4 依据真实数据生成，不引入未经验证的数据源。

## 4a. 审批与跨系统协同分类（预留）

### 4a.1 APPROVAL（审批）

面向审批流程类请求，例如：

- 查询审批状态 / 审批节点 / 审批待办
- 发起投资、退出、处置等审批动作
- 审批意见 / 审批记录查询

**路由**：`A1(APPROVAL) → A5 审批处理`（挂载审批流程接口，如 OA 审批）。

**约束**：
- 审批动作为**高权限操作**，A5 必须校验用户权限与审批人身份，未授权时如实拒绝，禁止越权代批。
- 查询审批状态不修改数据，仅读取；发起审批属动作类，须有明确授权链。

### 4a.2 CROSS_SYSTEM（跨系统协同）

面向需**跨系统取数或动作**的请求，例如：

- 统一门户 / 蓝凌 OA / 用友 / 金蝶 / 业务系统之间的数据协同
- 某业务既在本问数系统、又在其他系统有对应数据
- 需要其他系统提供上下文或动作（如推送、同步、回写）

**路由**：`A1(CROSS_SYSTEM) → A6 跨系统协同`（挂载跨系统集成工具）。

**约束**：
- 跨系统取数同样遵循**数据忠实**原则：不编造、不臆断其他系统数据。
- 跨系统**动作**（回写 / 推送 / 同步）属高风险，A6 须校验授权与目标系统一致性后方可执行。

### 4a.3 优先级与判定边界

| 场景 | 判定优先级 | 说明 |
|------|-----------|------|
| 审批类 | 高于 QUERY | 含"审批/待办/审核"关键词 → `APPROVAL`，避免误归为数据查询 |
| 跨系统 | 需用户明确提及系统名 | "在 OA 里查" / "同步到 XX 系统" 等 → `CROSS_SYSTEM` |
| 审批 + 数据查询混合 | 以主导意图为准 | 先取数再审批 → 可 A2 → A5 串联（视 Chain 能力） |

> 两个分类为**预留分类**：当前阶段可先接入 L0 判定与路由，实际下游 Agent（A5 / A6）与接口联调待评审后实施。

## 7. 验收标准（评审通过后）

1. 对"新增记忆/修改规则/配置"类元请求，A1 **恰一次交接给 A3**，不再死循环、不再编造"已固化"。
2. 对"生成 Excel / 下载文件"请求，A1 正确路由到 A4，且文件内容与真实查询一致。
3. 对普通数据查询，A1 行为与现状一致（5 类分类 + 政府引导基金拆解）。
4. 对审批类请求（含"审批/待办/审核"），A1 正确路由到 A5，不误归为数据查询。
5. 对明确提及外部系统的跨系统请求，A1 正确路由到 A6。
6. 对歧义/无关请求，A1 一次交接给 A3 处理，无重复输出。
7. 全链路可观测：A1 输出始终包含 `[L0]` / `[L1]` / `[目标Agent]` 标记。
