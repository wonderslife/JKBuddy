## 1. 总体定位与核心判断

JKBuddy 的本质是**「企业级 AI 问数与业务办事平台」**，不是单纯聊天工具。其核心价值不在模型能力，而在 **LibreChat 多 Agent 编排 + 若依数据权限 + 统一门户身份 + 代码沙箱** 这套"受控的智能体接入层"。

**设计主轴（四不可割裂）**：
1. **身份与权限贯穿所有 Agent**
2. **能力以 MCP 工具为唯一入口**
3. **一切写操作经若依二次裁决**
4. **数据权限判定完全收敛在若依服务端**（agent/MCP 不做分类识别）

一旦割裂，产品会退化成"模型直连数据库"的裸查询，丧失企业适配性。

## 2. 技术底座

| 组件 | 选型 | 职责 |
|------|------|------|
| 对话中枢 | LibreChat | 多 Agent 编排、会话、记忆、MCP 挂载 |
| **核心模型** | **qwen3.6-35B（本地部署）** | 意图分类 / 工具调用 / 输出生成 |
| 能力接入 | MCP Server（每业务系统独立） | 查询 / 审批 / 多系统协同工具 |
| 权限系统 | 若依（RuoYi） | 功能权限 @PreAuthorize + 数据权限 @DataScope |
| 身份认证 | 统一门户 SSO（蓝凌 OAuth2） | 单点登录、身份透传 |
| 执行沙箱 | LibreChat 代码沙箱（code-command） | 文件导出、可视化、受限计算 |
| 数据底座 | 若依业务库 + DWD 只读视图 | 数据存储与预聚合 |

### 2.1 模型选型说明（qwen3.6-35B 本地部署）

- 取代此前讨论的 gemma-4-26B，作为 A1/A2 及下游 Agent 的默认推理模型。
- 因模型改为 **35B 本地部署**，需重新验证以下点（原防重机制仍须保留）：
  - 工具调用（function calling）的稳定性；
  - 多轮澄清是否仍会重复提问 → 保留 `recursion_limit` 硬限制与 `end_after_tools=true`（02/05 已固化）；
  - 本地推理延迟对并发的影响（见 §9）。
- 模型能力与具体微调细节不在本蓝图臆测范围，落地时以实测为准。

### 2.2 本体设计原则

本体采用**混合方案（共享核心 + 领域扩展）**，详见 [07-本体架构策略](07-本体架构策略（共享核心+领域扩展）.md)。核心原则性表述如下：

1. **共享核心管跨系统稳定语义**：企业/部门/人员/组织、审批(approval)、数据权限(data_scope)、通用枚举(金额单位/业务线骨架) 等**与数据源无关**的概念，抽离为 `platform` 共享核心本体，供所有业务系统复用。
2. **领域本体管绑定数据源的具体语义**：投资(Fund/Subfund/Project + DWD 白名单)、资产(资产/处置) 等绑定具体表/视图的语义，放在各业务系统自己的领域本体，**延续现有 `ontology.yaml`**。
3. **判定准则**：**是否绑定数据源（view/table）**——绑定 → 领域，不绑定 → 共享核心；含视图级安全白名单的必属领域。
4. **依赖单向**：领域本体 `imports` 共享核心，**禁止领域间互引**，避免依赖环。
5. **Skill 不持有语义**：Skill 仅做"本体→MCP 操作适配"，语义单一事实源始终在本体（延续 04 Q3）。
6. **版本治理**：共享核心严格版本化 + 中央评审；领域本体锁定核心版本、独立发布。

## 3. 核心组件集成与数据流转

**产品架构图**（含本体横切层）：

```
┌────────────────────────────────────────────────────────────────────┐
│                        统一门户（SSO 单点登录）                       │
│                      OAuth2 认证 · 身份透传(loginName)              │
└───────────────────────────────┬────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────┐
│                      LibreChat（对话中枢 / 多 Agent）                │
│    A1 意图路由 → A2 数据 / A3 系统 / A4 导出 / A5 审批 / A6 协同      │
│    会话/记忆(MongoDB) · qwen3.6-35B                                 │
└──────────┬───────────────────────────┬─────────────────────────────┘
           │ MCP 协议(携带身份,仅透传)      │ 生成 Web 页面 / 渲染指令
           ▼                             ▼
┌──────────────────────┐      ┌────────────────────────────────────┐
│  MCP Server(每系统独立) │      │  H5 渲染 / Artifact（AI 生成页面）   │
│  mcp-inv-server-v2(投资)│      │  · 系统 Web 页面 AI 生成            │
│  mcp-asset-server(资产)│      │  · 统一应用入口 · 交互式渲染         │
│  └─ 查询/审批/协同 工具   │      │  · 代码沙箱(code-command)承载      │
└───────────┬──────────┘      └────────────────────────────────────┘
            ▼  REST（身份 + 业务参数）
┌────────────────────────────────────────────────────────────────────┐
│                        若依（RuoYi）                                │
│   @PreAuthorize 功能鉴权 · @DataScope 数据权限判定（收敛在此）         │
│   业务 Service / 审批流程 / 多系统协同                               │
└───────────────┬────────────────────────────────────────────────────┘
                ▼
┌────────────────────────────────────────────────────────────────────┐
│                      数据底座（各业务库 + DWD 只读视图）              │
│   投资 <db-name> / 资产 <asset-db>                                  │
└────────────────────────────────────────────────────────────────────┘

横切层（贯穿全链路）：
  · 本体层：platform 共享核心 ← domain:investment / domain:asset（import 单向依赖，见 07）
  · 安全层：身份校验 · 参数白名单 · 数据权限 · 操作审计
  · 渲染层：AI 生成 H5/Artifact 页面，作为统一应用入口（LibreChat 渲染能力受限，需依托更完整平台，见 §11）
```

**架构形态**：**星型总线**——LibreChat 为对话中枢，所有能力以 MCP 工具为边界，避免 Agent 直连业务库。

**数据流转链路**：
```
统一门户(SSO) → LibreChat AuthContext → 会话上下文(identity)
   → A1 意图路由 → 下游 Agent
   → MCP Server（携带已认证身份，仅透传）
   → 若依：@PreAuthorize + @DataScope（数据权限判定）
   → 返回受控数据 / 执行审批 / 多系统协同
   → 代码沙箱（仅对已授权结果做导出/可视化）
```

**关键约束**：
- LibreChat ↔ MCP：经 mcpServers 挂载，工具以 `allowed-tools` 收敛到各 Agent。**MCP 工具是"业务能力点"，不是"模型自由调用点"**。
- 身份透传：MCP 仅透传已认证 loginName，**数据权限判定在若依**（06 §4）。
- 代码沙箱：仅接收 A2/A4 已授权结果，**不接触原始库**。

**潜在风险**：
- **身份伪造**：MCP 信任客户端自报 loginName → 越权。对策：仅信任 LibreChat 服务端注入的认证上下文，MCP 中间件校验会话有效（06 §4.6）。
- **工具暴露面过大**：MCP 工具注册过多 → 模型误用。对策：按 Agent 收敛 `allowed-tools` + 工具 docstring 声明边界（04 本体边界）。

## 4. 多 Agent 系统实现架构

**架构原则**：分层共享 + 职责收敛（05 文档）。

| Agent | 类型 | 工具 | 职责 |
|-------|------|------|------|
| A1 意图路由器 | 分类器（零工具） | 无 | L0 意图门 + 参数提取 + 交接 |
| A2 数据执行器 | 执行器 | 查询类 MCP | 调工具查数、数据忠实输出 |
| A3 系统处理 | 执行器 | 系统/澄清 | 元请求、歧义澄清、无关说明 |
| A4 文件导出 | 执行器 | 代码沙箱 | 基于已授权结果导出 |
| A5 审批处理 | 执行器 | 审批类 MCP | 审批流转（若依裁决） |
| A6 跨系统协同 | 执行器 | 协同类 MCP | 跨系统动作 |

**任务分配与协作**：A1 通过 Chain/Handoff 分派；**交接契约"恰一次、之后停止"**（05 §4），杜绝 A1 死循环。

**冲突解决**：
- 工具竞争 → `end_after_tools` + 每 Agent 收敛工具集。
- 语义冲突（政府引导基金拆解）→ 固化于 A1 指令/Skill，单一事实源（04 本体）。
- 角色冲突（领导/员工/审计）→ Chain 上下文传角色，A2 角色感知输出（02）。

**潜在风险**：
- Agent 级联放大幻觉 → A1 输出结构化（L0/L1/参数/目标Agent）+ 可观测标记。
- 递归失控 → `recursion_limit` 硬限制 + `end_after_tools=true`。

## 5. 统一门户单点登录（SSO）

**技术选型**：蓝凌 SSO + OAuth2 授权码模式。LibreChat 为 OAuth2 Client，统一门户为 IdP。

**认证流程**：
```
未登录访问 → 重定向统一门户 → 门户认证 → 回调带 code
 → LibreChat 换 token → 拉用户信息 → 建立本地会话(loginName)
 → 后续请求携带身份 → MCP 透传 → 若依判定
```

**集成要点**：
- 双开关：`MK_SSO_ENABLED`（后端）+ `VITE_MK_SSO_ENABLED`（前端跳转）；**VITE_ 为构建期变量，改动须重建前端**。
- SSO 管理员名单：`MK_SSO_ADMIN_ACCOUNTS`。
- 会话过期：`SESSION_EXPIRY` 按企业安全要求调整。

**潜在风险**：
- 认证绕过 → `MK_SSO_ENABLED=false` 时同步不注册 `/ssoLogin` 路由。
- 缓存陈旧用户 → 改用户文档须使会话缓存失效，避免 OpenID JWT 突发缓存返回旧 `req.user`。

## 6. 权限管理细粒度控制

**双层权限**（全部由若依裁决，06 核心原则）：
- **功能权限**：菜单/操作 → `@PreAuthorize`。
- **数据权限**：`data_scope`（1全部/2自定义/3本部门/4本部门及以下/5仅本人）→ `@DataScope`。
- **能力权限**：MCP 工具按 Agent 收敛（`allowed-tools`）。

**用户角色**：领导 / 员工 / 审计 三类画像（02），映射到若依 `sys_role`。

**操作审计**：每次查询/审批/协同留痕（发起人、范围、时间）。

**潜在风险**：
- 口径漂移 → 强约束"判定收敛在若依，agent/MCP 不做分类识别"。
- 越权代批 → 审批一律经若依 REST，`@PreAuthorize`+`@DataScope` 双校验。

## 7. 功能优先级与迭代路线

**MVP（最小可行产品）**：
1. 单点登录 + 用户身份打通
2. A1 意图路由 + A2 基础查询（若依权限受控）
3. 表格/文字输出（数据忠实）
4. 审批状态只读查询（待办/状态）

**P1（增强）**：审批动作、文件导出、多系统协同。
**P2（规模化）**：跨系统协同深化、审计报表、性能优化。

**理由（辩证）**：先证明「权限受控的查询」闭环可行，再上写操作，避免早期暴露审批/协同高风险面。

**潜在风险**：MVP 范围蔓延 → 用"每个版本一个可验证闭环"约束。

## 8. 用户体验设计

- **交互流程**：未登录一键跳转门户，回跳免重复登录；对话即入口，Agent 路由透明；歧义最小澄清（≤1 轮、给候选）。
- **界面布局**（政务端庄风，蓝 #1e3a5f + 金 #d4af37）：左导航路径树（逐级累积高亮）+ 主对话区 + 结果表格区；结果附数据来源/条数/时间戳。
- **响应反馈**：工具调用中显示"查询中"；无数据显示"无数据"而非编造；审批成功/403 明确反馈。
- **潜在风险**：过度拟人/冗长 → 结构化表格 + 关键洞察（领导版 3 行洞察）。

---

## 9. 性能与可扩展性

- **并发处理**：LibreChat/MCP 无状态 → 横向扩容；后端数据库并行读取（避免串行往返）。
- **数据存储**：业务数据在若依库；DWD/本体只读视图；会话/记忆在 LibreChat（MongoDB）；缓存短 TTL。
- **水平扩展**：每业务系统独立 MCP Server（06）→ 隔离故障域、独立扩缩；MCP 多实例 + 负载均衡；认证无状态（JWT）。
- **模型推理（qwen3.6-35B 本地）**：关注本地推理吞吐对并发的制约，必要时做并发限流/排队，避免推理队列打爆。
- **潜在风险**：大数据量查询慢 → DWD 预聚合 + 索引（04）；沙箱资源耗尽 → 限时/限资源。

---

## 10. 安全防护体系

- **数据加密**：传输 TLS；敏感字段按权限脱敏；密钥存 `.env`/KMS，不入库不入 Git。
- **漏洞防护**：
  - 认证：OAuth2 + 服务端身份校验，防伪造；
  - 注入：MCP 工具参数白名单 + 参数化，防 SQL 注入；
  - 沙箱：隔离执行，防命令注入/路径穿越；
  - SSO：禁用时路由不注册，防旁路。
- **合规**：数据权限最小化；操作审计留痕；公开仓库脱敏（JKBuddy 规则）。
- **潜在风险**：安全与易用冲突 → 以"默认最小权限"为原则，特殊放行需显式配置。

## 11. 更完整平台诉求

### 11.1 LibreChat 受限点（目前发现，促发更完整平台）

在 JKBuddy 的设计与落地实践中，发现 LibreChat 在以下方面存在限制，成为**必须依托更完整承载平台**的动因：

| # | LibreChat 受限点 | 影响 | 诉求 |
|---|----------------|------|------|
| 1 | **渲染 / Artifact 能力弱**：默认以聊天 UI 为主，对"AI 生成可交互系统 Web 页面（H5/Artifact）"支持有限 | 难以作为统一应用入口提供丰富交互 | 需 H5 渲染 / Artifact 工具，AI 生成系统页面并承载交互（见 §3 渲染层） |
| 2 | **多 Agent 编排靠 Chain/Handoff 手工配置**：A1-A6 复杂业务流（审批/协同/跨系统）依赖指令与配置拼接 | 审批状态机、多系统事务难以在平台内表达 | 需平台级工作流 / 审批 / 任务编排引擎 |
| 3 | **MCP 工具是"能力点"非"流程"**：无法表达审批状态机、跨系统事务语义 | 写操作与协同缺乏流程语义 | 需平台级业务流程 / 状态管理 |
| 4 | **无内置权限模型**：数据权限依赖若依二次裁决（06），平台内缺少细粒度资源授权 | 权限治理分散在外部系统 | 需统一身份 / 授权 / 审计底座 |
| 5 | **无内置本体层**：语义靠 Skill/指令维护（04/07 引入外部本体方案） | 多系统本体统一需外部支撑 | 需平台级语义 / 本体治理 |
| 6 | **会话/记忆仅限聊天场景**：难以承载"统一应用入口"式的持久化应用状态 | 应用页状态、工作台难持续 | 需平台级应用状态 / 工作台承载 |
| 7 | **模型单一绑定**：本地模型 qwen3.6-35B 的 function calling、并发推理吞吐受限（§2.1/§9） | 大并发与复杂工具调用受限 | 需平台级模型路由 / 限流 / 弹性 |

> 上述受限点指向一个更完整的**承载平台**（工作流、权限、渲染/Artifact、本体治理、模型路由、统一应用入口），而**不改变** JKBuddy 已固化的业务设计（多 Agent、MCP 化、若依数据权限、混合本体）。
