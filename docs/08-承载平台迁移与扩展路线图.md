# 承载平台迁移与扩展路线图

> **文档版本**：v1.0
> **生成日期**：2026-08-08
> **文档类型**：权威规格（路线图 / roadmap）
> **状态**：待评审（仅审阅，未改动生产）
> **目标**：针对 [01 蓝图 §11.1](01-JKBuddy产品设计蓝图.md) 列出的 **7 个 LibreChat 受限点**，规划一份**具体、分阶段、载体无关**的迁移/扩展路线图，说明如何利用 **openworker** 或**自建平台**补齐这些能力。
> **核心原则**：受限点只指向"承载层"的扩展，**不改变**已固化的业务设计（多 Agent、MCP 化、若依数据权限、混合本体）。

> **配套文档**：[01-JKBuddy产品设计蓝图.md](01-JKBuddy产品设计蓝图.md)（含 §11 受限点）、[05-A1设计方案.md](05-A1设计方案.md)（A1-A6）、[06-若依系统MCP化改造与数据权限设计.md](06-若依系统MCP化改造与数据权限设计.md)（MCP 化 + 数据权限）、[07-本体架构策略（共享核心+领域扩展）.md](07-本体架构策略（共享核心+领域扩展）.md)（混合本体）

## 1. 目标与总体原则

### 1.1 目标

将 JKBuddy 从"LibreChat 承载"演进为"更完整承载平台承载"，补齐 7 个受限点，形成**统一应用入口 + 平台级工作流/权限/本体/渲染/模型路由** 的企业级底座。

### 1.2 总体原则

1. **载体无关**：路线图按"能力层"规划，openworker 与自建平台是**同一套能力层的两种载体实现**，可替换、可共存、可演进。
2. **渐进迁移**：不"推倒重来"，按 P0→P4 逐阶段，每阶段一个可验证闭环。
3. **不破坏既有设计**：A1-A6、MCP 化、若依数据权限、混合本体保持不变，仅"承载"方式升级。
4. **LibreChat 降级为前端/推理旁路**：后期 LibreChat 退化为"对话式前端"或纯模型推理，业务能力由平台承载。

### 1.3 双轨策略

| 轨 | 说明 | 适用 |
|----|------|------|
| **轨 A：openworker** | 采用现成承载平台 | 若 openworker 具备所需能力、可控、可落地（**待调研**，见 §6） |
| **轨 B：自建平台** | 自研承载层（工作流/权限/渲染/本体/模型路由） | openworker 不满足或不可控时；或与现网若依深度耦合时 |

> 两者**不互斥**：可"openworker 为主 + 自建补齐缺口"，或"自建为主 + openworker 单点能力"。决策框架见 §6。

## 2. 受限点 → 能力映射

| # | LibreChat 受限点（01 §11.1） | 需补齐的平台能力 | 对应阶段 |
|---|------------------------------|----------------|---------|
| 1 | 渲染 / Artifact 能力弱 | **H5 渲染 / Artifact 服务**（AI 生成 Web 页面、交互式渲染、统一应用入口） | P0a/P0b |
| 2 | 多 Agent 编排靠手工 Chain/Handoff | **平台级工作流 / 任务编排引擎**（A1-A6 流程声明化） | P2 |
| 3 | MCP 工具是"能力点"非"流程" | **业务流程 / 状态管理**（审批状态机、跨系统事务） | P2 |
| 4 | 无内置权限模型 | **统一身份 / 授权 / 审计底座**（对接若依，细粒度授权） | P1 |
| 5 | 无内置本体层 | **平台级语义 / 本体治理**（承载 07 混合本体） | P1 |
| 6 | 会话/记忆仅限聊天场景 | **应用状态 / 工作台承载**（持久化应用页状态） | P3 |
| 7 | 模型单一绑定 | **模型路由 / 限流 / 弹性**（多模型、qwen 负载管理） | P3 |

## 3. 分阶段路线图（P0→P4）

### P0a：H5/Artifact 渲染载体调研与选型（前置阻塞项）

**目标**：确定 P0 的实现载体（openworker vs 自建），产出决策文档，消除"载体未定则无法启动"的阻塞。

**实现**：
- 完成 [§6 openworker 评估清单](#6-openworker-评估框架待调研) 的全部 7 个维度调研，形成结论。
- 同步评估**自建渲染沙箱**的技术选型（沙箱隔离方案、DSL 设计、与 LibreChat Agent 输出的对接方式）。
- 产出**载体决策文档**：轨 A（openworker）vs 轨 B（自建）的选型结论与依据。

**验收**：
- openworker 评估清单 7 维度均有结论（不再是 `<unsure>`）。
- 载体决策文档评审通过，明确 P0b 的实现路径。

### P0b：统一应用入口 + H5/Artifact 渲染实现（补受限点 1）

**目标**：基于 P0a 选型结论，最快见效——让 Agent 能"AI 生成系统 Web 页面"，提供统一应用入口与交互，摆脱"纯聊天"体验。

**实现（载体无关）**：
- 平台提供 **Artifact/H5 渲染运行时**：接收 Agent 生成的页面代码（HTML/CSS/JS 或声明式 DSL），沙箱渲染为可交互页面。
- 提供 **统一应用入口**：按角色/权限聚合 A2-A6 生成的页面，形成工作台/应用导航。
- **数据忠实约束**：页面中的每个数值必须来自工具真实返回的 `data`（延续 A2/05 数据真实原则）。

**验收**：
- 至少一个业务场景（如"领导查询→生成投资概览仪表盘页"）端到端可交互。
- 页面渲染沙箱隔离，无命令注入/路径穿越（延续 01 §10）。

> **P0a → P0b 依赖**：P0a 为 P0b 的前置阻塞项，P0a 决策文档未通过评审前不进入 P0b 实现。

### P1：统一身份/授权/审计 + 本体治理底座（补受限点 4、5）

**目标**：搭好"身份-权限-语义"地基，供后续流程与渲染层复用。

**实现**：
- **统一身份/授权/审计底座**：延续 06——SSO loginName → 若依 sys_user → 数据权限判定在若依；平台补充细粒度资源授权（页面/工具/数据字段级）与操作审计留痕。
- **平台级本体治理**：承载 07 混合本体（共享核心 + 领域扩展），提供本体注册、校验、生成器、`get_ontology(scope)` 内省，替代"语义散落在 Skill/指令"。

**验收**：
- 平台新增资源（页面/工具）可复用统一授权模型，审计可查。
- 本体单一事实源由平台治理，领域本体 import 共享核心单向依赖生效。

### P2：平台级工作流 + 审批 + 跨系统协同（补受限点 2、3）

**目标**：把 A1-A6 的复杂业务流从"手工 Chain 配置"升级为"平台声明化工作流"。

> **与 01 §3.1 `BuddyGateway` 的关系**：本阶段以平台声明化工作流**结构性实现** 01 §3.1 描述的"受控网关统一调度"——当前由 LibreChat Agent 编排 + MCP 中间件 + 若依鉴权**分散承担**的网关职责（鉴权、本体注入、意图路由、工具受控），在此阶段收敛为平台级单入口工作流，交接契约"恰一次即止"由平台结构强制而非依赖 prompt 约束。

**实现**：
- **工作流/任务编排引擎**：把 A1 路由 + A2/A5/A6 的任务分派、状态流转、审批节点声明化（BPMN/DSL），平台调度。
- **业务流程/状态管理**：审批状态机、跨系统事务（06 的审批/协同动作）由平台承载状态与一致性，MCP 仍为执行通道、若依仍裁决权限。
- **交接契约保留**：延续 05 §4"恰一次、之后停止"，由平台工作流强制，而非依赖模型自觉。

**验收**：
- 资产处置审批（06 样例）经平台工作流 + 若依鉴权端到端跑通。
- A1 死循环由平台工作流结构上杜绝（不再依赖 prompt 约束）。

### P3：模型路由/弹性 + 应用状态/工作台（补受限点 7、6）

**目标**：规模化与"应用化"。

**实现**：
- **模型路由/限流/弹性**：多模型注册、按任务路由、qwen3.6-35B 本地推理并发限流/排队、failover（延续 01 §9）。
- **应用状态/工作台承载**：持久化应用页状态（非仅聊天记忆），支持工作台/收藏/草稿。

**验收**：
- 本地模型并发下吞吐可预期（有明确限流/排队，不打爆推理队列）。
- 工作台可持久化多个 AI 生成页面的状态。

### P4：收敛迁移

**目标**：全量接管，LibreChat 降级为旁路。

**实现**：
- 业务能力（查询/审批/协同/渲染/权限/本体）全部迁移至平台；LibreChat 退化为"对话式前端"或纯推理后端。
- 存量会话/数据平滑迁移。

**验收**：核心业务在平台上全量可用，LibreChat 仅作可选前端/推理旁路。

## 4. 双轨落地对照（openworker vs 自建）

| 能力层 | 轨 A：openworker | 轨 B：自建平台 |
|--------|-----------------|---------------|
| H5/Artifact 渲染 | 若提供则复用 | 自研渲染沙箱 + 应用入口 |
| 工作流/审批引擎 | 若提供则复用 | 自研工作流（可借 BPMN 引擎） |
| 统一身份/授权/审计 | 若与若依可对接 | 自研授权中间件 + 审计 |
| 本体治理 | 若提供语义层 | 自研本体注册/校验/生成器（延续 07） |
| 模型路由 | 若提供 | 自研路由/限流/排队 |
| 与现网（若依/MCP/SSO）集成 | 需评估适配成本 | 天然可控 |

> **轨 A 依赖 openworker 实际能力**，未经调研不得假定其具备/不具备上述能力（见 §6 评估清单，**待调研**）。

## 5. 迁移顺序与依赖

```
P0 渲染/入口 ──→ P1 身份/权限/本体 ──→ P2 工作流/审批/协同 ──→ P3 弹性/工作台 ──→ P4 收敛
    │                   │                      │                   │
    └─ 快速见效            └─ 地基                 └─ 流程化             └─ 规模化/应用化
```

**依赖说明**：
- P1 的权限/本体底座是 P2/P3 的前提（流程与工作台都要用身份与语义）。
- P0 可先行，因渲染/入口相对独立、见效快。
- 每阶段完成后做"并行期"验证（新平台能力与 LibreChat 并存），再切换。

## 6. openworker 评估框架（待调研）

> ⚠️ **不确定声明**：目前对 openworker 的产品定位、API、能力边界、授权模式与现网兼容性**无确切信息**，以下为**评估清单（待补充调研后填充结论）**，不构成对其能力的任何断言。

<unsure> openworker 的具体能力、部署方式、与 LibreChat/若依/SSO 的集成路径、授权与成本、可控性与合规性均需调研确认，暂不臆测。 </unsure>

**评估维度（问题清单）**：
1. **渲染/Artifact**：是否支持 AI 生成可交互 Web 页面/H5？是否可作为统一应用入口？
2. **工作流/编排**：是否提供声明化工作流、审批状态机、任务编排？能否替代手工 Chain/Handoff？
3. **权限模型**：是否提供细粒度授权？能否与若依 `@PreAuthorize`/`@DataScope` 对接、保持"判定在若依"？
4. **本体/语义**：是否提供语义层/本体治理？能否承载 07 混合本体（共享核心 + 领域 import）？
5. **模型路由**：是否支持多模型注册、限流、排队、failover？能否纳入 qwen3.6-35B 本地实例？
6. **集成与数据**：MCP 工具、SSO loginName 透传、若依 REST、代码沙箱如何接入？
7. **可控与合规**：部署形态（私有化？）、授权成本、审计能力、是否满足政务端庄/数据权限最小化要求？

> 调研完成后，将各维度结论填回本文档 §4 对照表与 §7 风险，形成最终"轨 A/轨 B"决策。

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| openworker 能力不符或不可控 | 保持"载体无关"；轨 B 自建作为兜底，避免单点绑定 |
| 迁移期双轨并存导致混乱 | 每阶段"并行期验证" + 明确切换点；能力按层剥离 |
| 工作流化引入新的复杂度 | 先声明化"审批/协同"等确定性流程，查询类保持 MCP 直通 |
| 自建成本高 | 优先复用成熟组件（BPMN 引擎、渲染沙箱、限流网关），仅领域逻辑自研 |
| 数据权限口径漂移 | 延续 06：判定收敛在若依，平台/Agent 不透传数据权限、只透传身份 |

## 9. 验收标准（评审通过后）
